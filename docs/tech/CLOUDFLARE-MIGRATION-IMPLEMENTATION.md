# Cloudflare migration implementation

Started **4 November 2026**, following the founder's instruction “ok, start working on it”. Permanent target: **https://recap.filternode.dev**. The [migration plan](CLOUDFLARE-MIGRATION-PLAN.md) remains the acceptance and retirement contract. This increment prepares the duplicate; it does not establish cutover or continuous operation.

## Implemented

- Two primary Workers: web/assets/API/catalogue and private queue-backed jobs, plus a private source gateway/Node container prepared for the paid phase. The existing 14 HTTP handler families and eight background task kinds are reused behind request-local environment/network adapters. Existing Netlify delivery stays available as code during the transition.
- Explicit route priority for API/catalogue/sitemap/robots and legacy aliases; unknown APIs and scheduler URLs cannot fall through to the SPA. Security/cache/indexing headers, five endpoint rate limits and a safe release-status response are included. Shadow responses remain noindex.
- Shadow mode has no crons/consumers and blocks private operations. Its frontend build omits production Clerk/Supabase credentials so direct browser-to-database saves cannot bypass the server's shadow guard.
- Durable queue admission, repeated-slot deduplication, per-pipeline serialization, owner/epoch/release checks, uncertain-outcome retention and acknowledgement without blind paid retries. Manual keyword generation uses private database payload storage; queue messages contain only opaque identities.
- Additive, private hosting control/work tables and service-only RPCs. Ownership/release changes require paused admission and drained active work. Existing source, financial, review and reader tables are untouched.
- Pinned Wrangler/Miniflare tooling, deterministic release SHA/Worker/configuration/asset hashes, actual workerd checks with outbound networking blocked, and a GitHub workflow that checks a commit before deploying its inert duplicate. Documentation-only pushes do not trigger that new deployment workflow. An active host cannot be overwritten by the shadow deployment command.

## Remaining gates

**Billing:** Cloudflare rejected an explicit CPU-limit deployment with error **100328**, stating that the account is on Workers Free. The duplicate can be prepared without CPU-limit configuration; the planned longer CPU allowance requires Workers Paid. No subscription was purchased. Containers is also a Paid-plan product; that same US$5 base currently includes 25 GiB-hours of container memory, 375 vCPU-minutes and 200 GB-hours of disk. At one running hour/day, a lite instance would use 7.5 GiB-hours, at most 112.5 vCPU-minutes and 60 GB-hours per 30-day month; this is a sizing example and allowances are shared across the account. Worker/Durable Object requests, network egress and usage beyond included quantities have separate meters. See [current official container pricing](https://developers.cloudflare.com/containers/platform/pricing/). Current published Workers starting price is US$5/account/month, with usage allowances and overages; approval is still required before changing the subscription under the project's no-new-subscription boundary. The current `/containers/applications` and registry APIs independently return HTTP 401 with an explicit Workers Paid requirement. The cached Wrangler OAuth session reports missing `containers:write`; that is not proof of the supplied API token's scopes. A separately supplied candidate token can read Workers but cannot read Queues/DNS, so it did not replace the verified deployment token. Container permission verification remains pending behind the account entitlement gate; no additional token request is needed yet.

**Source transport:** a plain `node:tls` test accepted a wrong certificate hostname under workerd, so that implementation was removed. Cloudflare's socket API passed locally but **accepted both the correct and wrong certificate hostname in the hosted runtime**. That implementation was removed too. The prepared replacement reuses the existing native Node downloader inside a pinned Linux/amd64 container, behind a private service binding. Its Node TLS stack accepts the correct hostname and rejects the wrong one with `ERR_TLS_CERT_ALTNAME_INVALID`; the container HTTP endpoint also returned a bounded real DNS-infrastructure response. Hosted container verification remains a mandatory gate. The source gateway has one lite instance maximum (256 MiB, 1/16 vCPU, 2 GB disk), sleeps after one idle minute and enforces 3,000 requests per UTC day in its coordinator. This is an operator cost guard for the current owner scope, not a newly advertised reader allowance. The container gets no database, model, identity or scraper credentials. `SOURCE_TRANSPORT_VERIFIED` defaults false; no source download or active-runtime entry is allowed through that adapter until the hosted proof succeeds. No creator source was contacted for these tests; the probes use public DNS-provider infrastructure only. This gate is not bypassed by local unit tests or a successful bundle upload.

**Cutover:** the old site remains credit-disabled. Its absence of execution is not a durable fence against a later credit reset. Before enabling Cloudflare, prove an independent old-host stop or revoke its exact project service credential after provisioning/verifying the replacement and draining known work. Keep all old reservations/provider references/unknown charges. No real review is approved and reminders remain off.

**Acceptance/retirement:** real origin/login/owner/ordinary/anonymous tests, complete route/data parity, checked automatic deployment, source compatibility, preserved native state and the bounded acceptance window still precede Netlify deletion. No old site, database or unrelated Cloudflare resource is deleted by this increment. Existing stalled ingestion and awaiting-review briefings remain product defects.

No new scraper/model execution or reminder sending was performed. Ordinary hosting, API-read and deployment usage is unmeasured. The reviewed artifacts and native hosted evidence are committed for handover; the running shadow copy is not a completed migration.

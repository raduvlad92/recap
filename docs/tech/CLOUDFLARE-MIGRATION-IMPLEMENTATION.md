## Implemented

- Two primary Workers: web/assets/API/catalogue and private queue-backed jobs, plus a private source gateway/Node container prepared for the paid phase. The existing 14 HTTP handler families and eight background task kinds are reused behind request-local environment/network adapters. Existing Netlify delivery stays available as code during the transition.
- Explicit route priority for API/catalogue/sitemap/robots and legacy aliases; unknown APIs and scheduler URLs cannot fall through to the SPA. Security/cache/indexing headers, five endpoint rate limits and a safe release-status response are included. Shadow responses remain noindex.
- Shadow mode has no crons/consumers and blocks private operations. Its frontend build omits production Clerk/Supabase credentials so direct browser-to-database saves cannot bypass the server's shadow guard.
- Durable queue admission, repeated-slot deduplication, per-pipeline serialization, owner/epoch/release checks, uncertain-outcome retention and acknowledgement without blind paid retries. Manual keyword generation uses private database payload storage; queue messages contain only opaque identities.
- Additive, private hosting control/work tables and service-only RPCs. Ownership/release changes require paused admission and drained active work. Existing source, financial, review and reader tables are untouched.
- Pinned Wrangler/Miniflare tooling, deterministic release SHA/Worker/configuration/asset hashes, actual workerd checks with outbound networking blocked, and a GitHub workflow that checks a commit before deploying its inert duplicate. Documentation-only pushes do not trigger that new deployment workflow. An active host cannot be overwritten by the shadow deployment command.

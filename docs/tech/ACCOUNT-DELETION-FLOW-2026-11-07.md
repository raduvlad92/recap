# Account deletion and linked identity integration — 7 November 2026

This increment integrates PR19 `c8dafc4` into PR17 on top of core main `1824574`. It completes the confirmation and inactive alias-aware cleanup implementation. It does not activate deletion or linked identity, alter a production setting, apply a hosted migration, select an existing reader for deletion, or prove real Clerk/backup erasure. Shared project status logs remain parent-owned. All native replies and identities used in tests are synthetic.

## Request, status and browser behavior

The existing Settings dialog now offers a distinct **Delete account** action when the server's own status endpoint is available. The existing workspace-clear action retains its separate meaning. Typed `DELETE` is required before the exact owner-free confirmation body is submitted. The server still requires signed recent factor ages, an exact active native session, same-origin request metadata and the explicit positive feature gate. A stale factor age returns the pinned Clerk SDK's reverification hint; `useReverification` prompts and retries. A token refresh alone cannot pass the server check. The request UUID survives SDK retries and uncertain replies.

Ordinary content and administrator authentication both resolve the stable owner, then always call `accountAccessAllowed(owner)`, including while lifecycle flags are off. The administrator allowlist and native session/user operations continue to use the actual provider subject. Read failures deny access; no email/name matching, owner rewriting or privilege migration is introduced.

`resolve_account_deletion_owner(issuer,subject)` is service-only. It accepts only the server's signature-verified identity and resolves an exact frozen locator to its existing tombstone, even if its alias is revoked or its issuer configuration later changes. Otherwise it uses the ordinary active-owner resolver. This exception is used only for own status and accepted-request replay; ordinary content, RLS, admin and reminders cannot use it. A revoked or unbound alias cannot initiate a new request. The native session's `user_id` is compared with the provider subject, while the recorded tombstone and data cleanup use the stable owner.

Before a potentially destructive POST, the browser removes the current stable owner's workspace cache and installs a versioned pending marker. Same-tab and storage events immediately fence outstanding tokens/saves/mutations. The reader hides its archive and content dialogs, aborts collection requests and clears local details. Late saves cannot restore the deleted cache. Other readers' caches and guest data are left alone. Signed-in accounts whose ordinary owner resolver is now blocked can still read their own deletion status.

A lost reply keeps the original pending identity and local suppression. A subsequent null GET is not proof that an earlier in-flight POST cannot commit, so it does not clear that marker. Reconfirmation replays the same UUID. Only a definitive pre-write reverification refusal can remove the provisional local marker; canceling that SDK prompt does not initiate deletion. Accepted requests are never cleared locally by a null status response. Session changes/unmounts fence late callbacks and cannot dispatch deletion or sign out a replacement session. After an accepted response, the reader receives a signed-out acknowledgement; a failed sign-out leaves an explicit retry and the workspace suppressed. The UI distinguishes pending, blocked and recorded-scope completion. It never claims universal erasure.

The six interface languages have corresponding deletion-flow copy. Qualified native-language review and hosted phone/keyboard checks remain pending. This is local UI/contract verification, not native browser evidence.

## Every frozen identity and restore generation

Migration `20261107224727_account_deletion_identity_flow.sql` follows lifecycle `203128` and identity `205636`. It creates private RLS-protected identity snapshots and append-only native steps, with no anonymous/reader/direct service-role writes. It changes no financial owner, reservation, fee, work identity or ceiling. Applying to an empty lifecycle table creates no request or work and leaves legacy mode/readiness unchanged.

Request acceptance takes the existing nonblocking exclusive owner barrier and configuration lock, validates the resolved owner, and freezes the original verified locator plus **all** mapped aliases, including disabled/revoked ones. Future links to a tombstoned owner or any frozen locator remain denied. Status replay cannot add a new locator. A locator already frozen for a different owner fails closed instead of being silently omitted from the snapshot. Existing single-identity tombstones are backfilled conservatively: old native evidence applies only to their exact original locator; any additional alias without proof reopens blocked cleanup rather than inheriting that evidence.

A leased worker handles at most **one pending native identity per invocation**. It checks lease authority, reads the exact user, bans/revokes it, deletes it, then confirms missing-user state. An absent user after a lost successful response is safe to acknowledge. Native steps append under the current restore generation and exact frozen locator. A missing/changed lease, mismatched native ID, unknown authority or failed/lost response blocks completion. The aggregate state machine refuses `identity_deleted` until every frozen identity has absence proof; normal financial/retention gates then still apply. Intermediate `identity_cleanup_pending` leaves suppression in place. Restoring a tombstone increments its generation; old native steps remain immutable history and cannot certify the new generation.

The currently configured `CLERK_ISSUER_URL`/`CLERK_SECRET_KEY` remain the default authority pair. A future cross-instance cutover may supply server-only `ACCOUNT_LIFECYCLE_CLERK_ISSUERS` JSON entries containing `issuer`, `secretEnv` and a nonempty `reviewRef`. `secretEnv` must name an already controlled `ACCOUNT_LIFECYCLE_CLERK_SECRET_*` binding containing a Clerk secret key; it cannot reference arbitrary application credentials. It is not a secret value. Only one exact issuer match is allowed. No credential or authority is inferred from a subject, email, browser value or arbitrary URL. Unknown/missing old-instance authority stays blocked. The existing fixed Clerk transport/host is reused; there is no new microservice, third-party destination or automatic secret provisioning. **No mapping or secret binding is configured by this increment.** Actual issuer/key-instance pairing still requires native operator proof before activation.

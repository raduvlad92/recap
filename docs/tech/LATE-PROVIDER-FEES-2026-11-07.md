## Finding and contract

The supplied 6 November observation is a completed YouTube run reporting **USD 0.004**, with an existing **USD 0** settlement and **USD 0.005** reservation maximum. This task does not refresh that observation or claim to have repaired the live balance.

`settle_collection_budget` treats any terminal numeric amount, including zero, as immutable. Replaying a different amount returns PT409. The hourly reconciler independently rejects a fee greater than its saved actual fee. Costs feed the global, reader lifetime and reader daily admission calculations through the reservation's cash projection; correcting a separate uncounted ledger would leave those calculations understated. Model accounting is a different ledger.

[Apify's run API](https://docs.apify.com/api/v2/actor-run-get) documents preliminary costs on the first completed response and recommends another read about ten seconds later. It also distinguishes authenticated owner costs from the narrower event-only information available to non-owners. A terminal status, elapsed age, empty dataset or successful content import cannot prove a free run.

This increment provides an **explicit server/operator library entry point**, `reconcileLateProviderFee(providerJobId, requestKey, env, fetcher)`, reusing the existing Supabase client and Apify request transport. It adds no route, cron, queue, deployed microservice, activation or automatic historical sweep. Calling it against production remains parent-owned work requiring the normal operational window and authorization. The implementation is not an invoice-finality guarantee.

The ordinary hourly worker now keeps a newly observed terminal zero fee unknown, with its hold intact. Genuine free runs can consequently remain held; this patch deliberately provides no age-based zero-cost certification. Existing positive-settlement and content-import behavior is otherwise retained.

## Exact checks

1. `prepare_late_provider_fee` accepts only an already-settled, launched, unparented Apify YouTube reservation joined to its exact saved provider job and collection ledger. Actor, run, owner/source, maximum and current actual fee must agree across those records. The provider job must be completed/failed. Unknown/held reservations, envelopes, social jobs and model charges cannot enter this path. Nothing selects work by age.
2. The server obtains only `GET actor-runs/<saved ID>` and `GET users/me`, with the existing configured provider token. It validates the saved Actor, current pinned build and exact authenticated provider owner. There is no provider POST, dataset retrieval, creator request, token export or runtime-flag enablement. Missing owner/build/cap proof fails closed. Organization/non-owner token cases need native validation and may safely refuse reconciliation.
3. Money travels as the original JSON decimal/exponent token, extracted only when unambiguous and consistent with the parsed numeric field. SQL independently validates those strings and uses exact `numeric` arithmetic, **rounding up to twelve decimal places**. No JavaScript floating point sum, inferred event pricing, clamp or epsilon tolerance decides the correction.
4. Recording requires current metadata, observed within sixty seconds, with no future/nonfinite observation time. A terminal run must have an actual finish timestamp at least ten seconds before the observation; this is only the documented preliminary-accounting check. A missing/zero fee never becomes final through this interval. The provider's reported run maximum must equal the saved reservation maximum exactly.
5. Under the existing policy → source → global-account lock order, the RPC locks and rereads the provider job, reservation and ledger. A revision covering their complete current rows is compared with the pre-request snapshot. Concurrent changes, including content/identity changes, reject a fresh receipt with PT409. No workspace/source/lease/content fields are updated.
6. Positive corrections must be at least the original settlement, both existing observed high-water amounts and all earlier receipt observations. They must fit the unchanged run maximum, global USD45 account ceiling, reader lifetime limit and the **original job UTC day's** reader limit, conservatively including all launched unknown holds. No current-day budget reset finances yesterday's charge.
7. An applied receipt and the three existing financial projections commit atomically. Only reservation actual/update time, provider-job actual/observed fee, and ledger observed fee/cost status/update time change. The existing ledger timestamp trigger remains active. The original settlement RPC is unchanged and still rejects a conflicting direct replay.

## Inspectable history and unresolved cases

`collection_provider_fee_receipts` is private and append-only, with RLS, no reader/anonymous access, SELECT/INSERT only for the existing server role and an immutable UPDATE/DELETE trigger. Both RPCs use `SECURITY INVOKER`, an empty search path and explicit service-only execution grants. No public view, browser parameter or user metadata grants authority. SQL trusts the existing private server to obtain authenticated provider evidence; possession of server credentials remains privileged authority.

Each receipt keeps its stable request key, exact provider-job/reservation/run links, authenticated evidence fields, response SHA-256, observation/finish timestamps, pre-request revision, full original reservation, original job financial fields, original ledger financial fields/timestamp, previous/reported/corrected amounts, delta and outcome. Raw provider bodies, credentials, private follows and job tokens are not saved in receipts.

The reservation and job amounts are **cash projections** corrected through this transaction; their original settlement remains inspectable in the immutable receipt. Later corrections add receipts rather than altering earlier receipts. Inspect receipts by `reservation_id`, ordered by `created_at,id`, alongside the original linked records. Money in the RPC result is returned as decimal strings.

An identical stable request key and recorded economic fields (including exact decimal tokens) returns the original receipt without charging twice. Fresh read time and response hash do not change that identity. Reusing a key for another job or changed economic fields is rejected. A new key is required for a new observation; a stale pre-request snapshot cannot create a second correction. Replaying an earlier unresolved observation does not turn it into a success as time passes.

Explicit persisted outcomes are `applied`, `unchanged`, `unresolved_nonfinal`, `unresolved_zero`, `unresolved_missing_fee`, `unresolved_decrease` and `unresolved_over_cap`. Invalid identity, stale evidence or CAS failure reject without creating an authoritative receipt. Unknown fees retain null; a prior observed amount is never substituted for missing provider metadata.

**Over-cap observations do not silently adjust money or limits.** Preliminary/nonterminal observations are also checked for overruns. They save an unresolved receipt and leave the original projections intact. Their existence blocks both new reservation insertion and first launch of an already-unlaunched reservation with PT402, under the same account serialization. The gate applies globally to source cash admissions, including an original-day reader-cap failure. This conservative stop requires separate audited resolution; this patch intentionally supplies no expiry, receipt deletion, flag reset or automatic reopening. Earlier over-cap evidence also remains a high-water lower bound if a later response reports less.

The seven historical unknown model charges and seventeen original held source reservations are outside this correction contract. They cannot be settled, released, overwritten or reused by it, and their age confers no authority. Existing IDs, launch references, maxima, timestamps, review state, reminder consent and supplier/model allowances remain protected.

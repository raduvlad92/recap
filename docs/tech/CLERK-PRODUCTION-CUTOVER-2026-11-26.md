## User migration and read-only rehearsal

1. The source instance, exact verified primary identities and stable workspace ownership are the authority. Get an approved roster for ordinary readers from the operator. A private JSON array of approved primary email addresses can supplement Clerk's exact allowlist. Use the known owner primary email separately. Inspect every existing workspace outside the roster before a global switch. Verify the old/new identities privately; do not use email equality alone to bind a new subject. Save pre-cutover readbacks for workspace, archive, library, settings and daily history.
2. Export the reviewed credentials into a private process environment with shell tracing off. Run `node scripts/check-clerk-production.mjs --inventory`. When the destination exists and DNS is ready, run `node scripts/check-clerk-production.mjs --preflight --plan-out .local/clerk-cutover-plan.json` once. The script emits public DNS and aggregate counts. The optional identity plan is mode 0600 and refuses to overwrite. Use a fresh `.local/` filename to rerun. The plan records the verified email, old subject, stable owner and any exact destination subject. Never share the plan or paste it into an issue.
3. Before import, rehearse the chosen sign-in. If approved users have passwords or TOTP that need preservation, use Clerk's protected Dashboard export and CLI import. Filter that export locally to the exact reviewed source subjects, preserve only the import columns needed and run `clerk migrate import <private-reviewed-csv> --source clerk --instance prod --dry-run`. Protect and remove the export under the credential-retention policy. The Backend API and ordinary CLI export cannot read password digests or TOTP secrets. Sessions, social links, and passkeys do not transfer. Require reauthentication or reenrollment for those. [Clerk instance migration](https://clerk.com/docs/guides/development/migrating/clerk-to-clerk)
4. For an approved passwordless account, create once with Clerk's verified primary email and `external_id` equal to the exact source subject, or migrate it through the reviewed Clerk import. Verify the returned production subject, exact external ID and verified primary email by rereading Clerk. If a create reply is missing or ambiguous, rerun destination preflight and reconcile by external ID before retrying. Out-of-roster destination accounts, duplicate identities, changed owners, unverified primaries and missing workspaces stop the switch. Never import editable role metadata or change owner IDs. [Clerk create-user contract](https://clerk.com/docs/reference/backend/user/create-user)
5. Before enabling production auth in Supabase, stage both old and new `(issuer, subject)` pairs against the same stable owner using `review_reader_identity_configuration` and `bind_reader_identity_alias`. These are the existing service-only reviewed identity operations. Preserve the starting mode while staging, enable lifecycle readiness for reviewed binding, include every still-required trusted issuer, and require an operator reference and a private review reference. In legacy mode, switch to linked mode after all required old and new aliases have been verified and before enabling the new issuer for browser traffic. Verify every alias, stable workspace owner and lifecycle fence. Keep the old aliases for rollback. [Stable reader ownership and RPC contracts](READER-IDENTITY-2026-11-07.md)

## Cutover and rollback

1. After the roster, DNS/TLS, approved import and aliases pass, capture old Worker versions and bindings, previous GitHub variable and config fingerprint, Supabase issuer settings, review receipt, and signed-in baseline. Schedule an approved independent auth window. Stage `pk_live_` and the corresponding live Worker keys/issuer against the same reviewed release. Keep existing processing and paid-wave decisions in effect.
2. Update Supabase third-party trust as rehearsed. Activate the checked reader build and both Worker configs together. Run `--accept` on real browser sessions. The owner and an approved ordinary reader must reach the same pre-cutover workspace and dated history/library. Confirm the ordinary reader cannot administer or reach another owner's data. Require a real normal sign-in for each enabled method that the roster depends on. A one-time ticket proves browser session routing and data continuity only. Record the release, verified checks and readback without identities or tokens.
3. On failure, restore the checked old reader assets, Worker versions/bindings, GitHub variable/build pin and old Supabase issuer trust. Keep reviewed legacy aliases active in linked mode so original sessions resolve their stable owners, then verify old normal sign-in and data readback. If required by the incident review, disable the new issuer and revoke its sessions after old access is restored. Avoid deleting accounts, revoking aliases or restoring data snapshots as part of routine rollback. The database owner keys and records were preserved through both releases.

## Three routes

1. **Keep feeds as the main discovery method and harden retries.** Preserve current native/Apify content handling, add source health alerts and catch-up reconciliation. Lowest change effort and supplier discovery costs, but RSS remains an unreliable single discovery dependency. This alone does not implement X/Instagram discovery or fix incomplete caption retrieval. Suitable only as an interim improvement.
2. **Official YouTube discovery plus selective content retrieval — recommended.** Resolve/cache each public channel's uploads-playlist ID, then check it hourly through the YouTube Data API. Retain RSS as a fallback signal. Only unseen video IDs enter the existing durable caption/content queue; prefer native existing captions and use capped, validated provider fallback. Add separate minimum-result managed discovery adapters for X/Instagram, measuring empty/unchanged-response charges before selecting a cadence. More implementation and one application Google API key, but aligns spending with new useful content. No creator OAuth/opt-in is needed for public metadata. Metadata discovery does not grant access to public creators' transcripts through Google's captions API.
3. **Managed providers for discovery and retrieval, with a second tested provider.** Use a managed supplier to inspect latest items and fetch content, retaining a validated fallback for real failures. This can simplify broad-platform access and supplier-side blocking maintenance, but creates more quiet-day lookups, provider dependence and potentially higher costs. Apify is already in use; Bright Data's documented capabilities/prices are an alternative to benchmark, not verified Therecap access. Never start both suppliers simultaneously or retry an ambiguous paid launch as a new job.

## Official API fit and cost boundaries

Google documents reading `contentDetails.relatedPlaylists.uploads` through `channels.list`, then reading that playlist through `playlistItems.list`. Both list calls cost one quota unit; playlist pages can contain up to 50 items. With cached playlist IDs, **21 channels × 24 hours = 504 quota units/day** for one page per check. An hourly batched `videos.list` metadata request brings that baseline to 528, before bootstrap, retries or extra catch-up pages. This fits within the current **10,000-unit/day default shared allowance**, assuming the application's actual allocation/other traffic permits it. Quota resets at midnight Pacific Time, distinct from our UTC supplier budgets. The inspected Google documentation does not establish a current dollar-per-call tariff; quota arithmetic is not a full operating-cost estimate. [Uploaded-video procedure](https://developers.google.com/youtube/data/guides/implementation/videos), [quota calculator](https://developers.google.com/youtube/data/determine_quota_cost), [playlist pagination](https://developers.google.com/youtube/data/reference/rest/v3/playlistItems/list), [public API-key example](https://developers.google.com/youtube/data/quickstart/js).

WebSub is an optional later speed improvement: Google pushes upload/title/description-change notifications to our callback. With hourly API reconciliation, it does not reduce that 504-unit baseline. It adds webhook/subscription management; Google's guide does not establish lossless delivery or a delivery-time SLA. The requested hourly cadence does not require adding this complexity immediately. [Official notification guide](https://developers.google.com/youtube/data/guides/push_notifications).

The official captions download method requires permission to edit the video. Therefore an API key solves public discovery/metadata, not transcript extraction from unaffiliated creators. Shorts/live readiness also needs explicit verification: public video metadata has no documented `isShort` flag, and discovery does not prove a live recording or captions are ready. [Captions permission](https://developers.google.com/youtube/data/reference/rest/v3/captions/download), [video schema](https://developers.google.com/youtube/data/reference/rest/v3/videos).

Current Apify Free-tier pricing lists US$4/1,000 primary videos, with separate date-range, transcript-minute and AI add-ons. If a naive hourly implementation billed one existing video each time, 21 × 24 × 30 × US$0.004 would be **US$60.48/month in primary-result fees alone**. This illustrates repeated-result waste; it is not a forecast or claim every unchanged/empty check is charged. Exact run minima, empty-result behavior and caption pricing must be measured under the selected configuration/caps. [Apify pricing](https://apify.com/streamers/youtube-scraper/pricing).

Bright Data advertises pay-as-you-go US$1.50/1,000 delivered records and a 5,000-record monthly free tier on its Web Scraper API page. Generic advertised record pricing does not prove the price, discovery completeness or full-content quality of our exact X/Instagram/YouTube requests. No account/plan or provider was activated in this research. [Vendor pricing](https://brightdata.com/pricing/web-scraper).

## Proposed next actions

1. Reconcile the four unfinalized hourly provider jobs using trusted stored references and provider GETs; retain holds until fees are known. Classify the 115 pending items into budget-delayed, temporarily inaccessible and captions genuinely unavailable. Do not re-post ambiguous jobs.
2. Implement hourly public uploads-playlist discovery with one restricted server-side API key, cached identities, pagination to the last known checkpoint and duplicate-ID protection. Keep source errors distinct from quiet sources. Add tested existing-caption fallback without generated transcription.
3. Implement minimal new-ID discovery for all ten followed X and eight Instagram accounts. Reuse evidenced suppliers where suitable; test burst/pagination/empty/unchanged costs and usable content. Share one public-source observation across overlapping follows as a later scale optimization while retaining private user workspaces and explicit cost allocation; do not silently change the billing model.
4. Add a visible per-source last-success time, discovery delay, pending-content age, budget-paused reason and recovery outcome. Alert the operator after two failed hourly cycles; keep per-source catch-up until its checkpoint is reconciled. Deduplication is already implemented; verify it across fallback suppliers too.
5. Run a **48–72-hour hosted acceptance period**, including a real new publication, unchanged source, induced failure/recovery, missed-run catch-up, duplicate event, live/Shorts readiness, budget stop and account isolation. Proposed target: discover within the next successful hourly cycle; retrieve available content with bounded retries, and explicitly label unavailable content. Never promise literal zero failures across external platforms.
6. Choose an explicit steady-state monthly ceiling from measured new-item volume and cost per usable transcript/post. The initial US$0.10/day cap is already delaying some retrieval; cheap operation and immediate retrieval of an arbitrary backlog cannot both be guaranteed by that cap. Keep existing limits until a revised budget is approved.

No application/schema/configuration changes, new supplier jobs, budget increases or live collection triggers were made for this comparison. Research used current official documentation, existing project evidence and read-only database summaries. Existing scheduled collection continues independently.

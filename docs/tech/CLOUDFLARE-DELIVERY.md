# Cloudflare handover delivery controls

Current checkpoint: 4 November 2026. PR #3 is merged as `63cf1be`. Its seven reported results pass, including the native neutral handover-journal probe; actual main shadow deployment and independent hosted preservation checks pass. The delivery adapter below is implemented and tested with isolated provider writes. Live verification uses metadata GETs only. No schedules, consumers or processing are activated.

`scripts/cloudflare-handover-delivery.mjs` operates only the existing `therecap-jobs` / `therecap-jobs-dead` queues, the three Therecap Worker schedule inventories and `raduvlad92/recap`'s existing `HOSTING_TARGET` variable. It accepts the full checked active artifact and ready handover plan, never an apply flag or caller-supplied activation policy. Before each write it verifies the expected database owner/epoch/release/pause/fence/revision and Worker versions/bindings/flags, obtains fresh external authorization and acknowledges a durable sub-operation intent. It repeats the checks after acknowledgement. The trusted executor must provide those external evidence/fence/head checks and durable storage; that composition is still unfinished.

Configuration happens only with Cloudflare ownership paused, old-host fencing established, no unresolved hosting work and exact staged active web/jobs versions. The consumer is created before cron triggers. The policy keeps the seven existing scheduled kinds behind the hourly/every-five-minute expressions and gives private keyword learning no cron. Reminders remain off. The consumer uses batch size 1, maximum concurrency 6, three retries, a 60-second default retry delay, a one-second batch wait and the existing dead-letter queue. Batch size 1 preserves the per-worker wall-time allowance; the global concurrency bound avoids unbounded autoscaling. Domain leases, financial reservations and uncertain-call handling still decide whether any paid operation may run.

Recovery's stop operation first pauses automatic deployment and clears only the known jobs schedules. It retains the existing consumer so admitted work can drain while the old Cloudflare release is still active. It does not delete queued work, inspect/purge messages, reset leases or settle financial holds. The later checked pause/restore operations still require drained work. Unexpected web/source schedules, unknown jobs crons, foreign/unbounded consumers and any dead-letter consumer stop progression instead of being overwritten.

Selection changes only the existing `HOSTING_TARGET` variable. It requires delivery readback and a saved witness of the prior variable value/update time, and rechecks delivery immediately before selecting Cloudflare. Lost successful consumer/schedule/target replies reconcile by native readback. Operator revision changes or a changed target witness stop a retry. All production writers must share the existing hosting concurrency group; these provider APIs do not form an atomic transaction. Selection uses existing local operator GitHub authority: the implementation does not export that credential to CI or assume the default Actions token can write repository variables. The executor must persist the returned target witness and sub-operation intents alongside its main journal before exposing an apply workflow.
